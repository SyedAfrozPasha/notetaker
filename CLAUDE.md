# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

Implemented and tested — see `notetaker/` for the code and `tests/` for the suite (383 tests, including two integration tests — a real-model faster-whisper test and a real-brew formula test). The original design spec ([docs/superpowers/specs/2026-09-11-notetaker-cli-design.md](docs/superpowers/specs/2026-09-11-notetaker-cli-design.md)) is still useful background on the "Approach A vs B vs C" rationale, but the code and this file are now the source of truth — keep the architecture summary below in sync with the code, not the spec, when either changes. `CONTEXT.md` and `docs/adr/` capture domain terms and key decisions made during implementation.

## What this project is

A macOS CLI tool (`notetaker`) that:
- Records the system audio of an ongoing Microsoft Teams meeting via a Core Audio process tap (macOS 14.2+; BlackHole loopback as the configurable fallback), plus your own voice from the default microphone.
- Transcribes it live using a local `faster-whisper` model, in ~10s rolling chunks (not true word-by-word streaming — see the spec's "Approach A" rationale).
- Sends the finished transcript to a pluggable AI provider (Claude by default) to produce a summary, action items, and tags.
- Saves each meeting as a single Markdown file with YAML frontmatter under a configurable notes directory.

Installed by cloning the repo and running a setup script (`./install.sh`) — no package registry involved.

## Planned architecture (from the spec)

Two run modes coordinating entirely through the filesystem under `~/.notetaker/` (a PID file, a per-session working directory, and a config file) — no daemon socket, no database:

- `cli.py` — command dispatch (Typer) for `init`, `start`, `stop`, `list`, `show`, `resummarize`, `set-api-key`, `show-api-key`, `menubar`, `dashboard`. `start`/`stop` show a `rich` loading spinner, since both can block for an unpredictable duration (spawning the recorder; the summarization API call). `init` shows a spinner for the setup checks and a spinner + elapsed timer for the Whisper model, driven by `service.ensure_whisper_model(on_phase=…)` phases ("Downloading … from Hugging Face (one-time)" only when `whisper_model_is_cached` is false, then "Loading …") — faster-whisper's own download prints nothing, so this is the only feedback during a multi-hundred-MB first run. `dashboard` is the one-process UI: it refuses up front if port 8420 is taken (`dashboard.port_in_use_error`), starts the web server on a daemon thread (`dashboard.serve_in_background`), then hands the main thread to the rumps menu bar app — so a recording started in the browser is always visible in the menu bar. `menubar` runs the menu bar alone, without the web server.
- `menubar.py` — a minimal `rumps`-based menu bar app: one-click Start/Stop, the dashboard's logo as the strip icon (`assets/menubar-idle.png`, a template image macOS tints, when idle; `assets/menubar-recording.png`, the full-colour red logo, plus the elapsed `MM:SS` while recording; no text when idle; both generated PNGs, 44px for Retina). Stop is non-blocking: `_stop` calls `service.begin_stop`, the strip shows "Saving…" while the shared `StopJob` runs, and the tick after it finishes reports the outcome once (notification, or an alert on error), an "Open Dashboard" item when constructed with `dashboard_url` (as `notetaker dashboard` does), and native notifications on save-complete, summarization-failure, and crash-detected. Polls `service.check_and_salvage_orphan`/`get_current_session_status` every second (so the timer ticks smoothly) — the first UI surface besides the CLI to call these on its own cadence, which is why `check_and_salvage_orphan` now claims the session file atomically before salvaging.
- `dashboard.py` — a `FastAPI`/`Jinja2`/`htmx` local web dashboard, bound to `127.0.0.1` only; htmx is vendored under `notetaker/static/` (served at `/static`) so the dashboard works offline. Styling is hand-written CSS in `base.html` (system font, CSS variables, automatic dark mode) — no framework, no build step. One polling endpoint (`GET /status`, polled every 2s by the page itself) renders the same `_status.html` partial that `POST /start`/`/stop`/`/cancel` also render, so htmx can swap a single status `<div>` regardless of which endpoint responded. The live view shows a pulsing timer, the transcript as per-speaker rows (`parse_transcript_rows` splits `[hh:mm:ss] Me:`/`Others:` and the recorder's status lines; the `_transcript.html` macro renders them, shared with the note detail page), a segment count and "last transcribed Ns ago" from the transcript file's mtime, and a small script in `base.html` keeps the pane scrolled to the newest line unless the reader scrolled up. Start-time routing warnings are kept in the module-level `_start_warnings` dict (keyed by session dir, cleared when the session ends) so they stay on screen across polls instead of vanishing on the next 2s swap. `POST /stop` does not block: it calls `service.begin_stop`, which runs `stop_session` on a background thread (`service.StopJob`, one per process, shared with the menu bar so a stop pressed on either surface shows on both); `/status` renders the job's current phase ("Summarizing... chunk 2 of 3") while it runs and, once the Note exists (and finished within the last 60s), answers with an `HX-Redirect` to `/notes/{id}?saved=1` so the page lands on the finished note (a saved banner, or a summarization-failed warning); `/start` is refused while a job runs. Piggybacks `check_and_salvage_orphan` onto its own status poll — the dashboard's own crash-detection cadence, independent of (and made safe alongside) the menu bar app's. Also serves a notes-management surface (`GET /notes` browse/search, `GET /notes/{id}` detail with copy buttons, `GET`/`POST /notes/{id}/edit`, `POST /notes/{id}/delete`, `POST /notes/{id}/resummarize`) as plain multi-page navigation over `service.py`. Also serves a `/settings` page for config editing (`notes_dir`/`whisper_model`/`ai_provider`, via `POST /settings/config`) and Claude API key management (masked view, live-validated set via `POST /settings/credential`, Keychain-backed) — this closes out the design spec's full Dashboard feature list.
- `service.py` — all operational logic (start/stop/list/show/init/cancel), used by `cli.py` and (from here on) every other UI surface. `begin_stop`/`current_stop_job` run a stop on a background thread as a process-wide `StopJob` (phase, note_path, error, finished_at) so the menu bar and dashboard, which share a process, both see it. Heavy third-party imports (faster-whisper via `download_model`/`transcriber.WhisperModel` wrappers, the `anthropic` SDK inside `ClaudeProvider`) are lazy so the CLI shows its first output in well under a second instead of after seconds of import. Raises `ServiceError` for user-facing failures; never prints anything itself — `cli.py` is a thin adapter that translates its results into `typer.echo` calls and exit codes. Detects and salvages an Orphaned session (a crashed Recorder from a previous run) via `check_and_salvage_orphan`, called before every `start`; `cancel_session` discards an in-progress Session without producing a Note. Every `stop`/salvage also writes a `<note-id>.transcript.txt` sidecar next to the note, preserving the raw transcript for future resummarization.
- `credentials.py` — provider-agnostic Keychain read/write/masking (`get_provider_credential`, `set_provider_credential`, `mask_credential`). Never stores a Provider credential in `config.yaml` or any plaintext file. `get_provider`/`check_setup` check the Keychain first, falling back to the credential's environment variable for backward compatibility.
- `systemaudio.py` — Core Audio *process tap* (macOS 14.2+): `create_system_audio_tap(bundle_id=None)` builds a `CATapDescription` (global, or one app's audio when `tap_process` names a running bundle id — falls back to global otherwise) and wraps it in a **private aggregate device** that PortAudio can open as a normal input. Deliberately not bound to any output device, so speaker/headphone switches mid-meeting don't matter. Uses ctypes + the PyObjC Cocoa package `rumps` already requires; all bindings load lazily via `_bindings()` so tests fake them. Two hard-won facts: the aggregate delivers **no samples until some app has played audio** (handled by `LiveCapture` padding), and a private aggregate **outlives the process unless destroyed** (handled by `recorder.main`'s teardown). See ADR 0004.
- `recorder.py` — background process (spawned by `start`, killed via SIGTERM by `stop`, SIGKILL after a 30s grace period). CLI is argparse (`--system-audio tap|blackhole`, `--tap-process`, `--system-device`, `--mic`, `--model`, `--model-path`). `LiveCapture` keeps two `sounddevice` input streams open for the whole session — your microphone (macOS default input; disabled by `capture_microphone: false`) and the meeting audio (tap aggregate, or BlackHole) — and writes one stereo WAV per chunk, **left = Me, right = Others**. Every source's first block is preceded by lead-in silence equal to the time since the streams started, so the channels stay aligned even though a tap delivers nothing until an app plays (without this the mic's echo of the speakers landed seconds away from the tapped original and the echo filter never matched). The first source is the clock; the other is padded with silence if it hasn't delivered (a disconnected headset is reported once into the transcript). Capture stays on the main thread; a single worker thread transcribes finished chunks in order and deletes them. A failed transcription of one chunk is logged and recording continues; only a capture failure ends the session. If the Others channel stays silent while Me has audio, a mode-specific routing warning is appended once — after 3 chunks in BlackHole mode, 18 in tap mode (a tap is legitimately silent until an app plays). **Teardown in tap mode: destroy the aggregate + tap, then `os._exit`** — never `Pa_StopStream` the tap aggregate; it deadlocked inside CoreAudio (`AudioDeviceStop` → `HALB_Mutex::Lock`) in end-to-end runs. `portaudio_device_index` re-initializes PortAudio and polls ~5s because Core Audio publishes a new device asynchronously. `check_output_routing`/`check_microphone_routing` give BlackHole-mode `start` its up-front warnings (returned on `SessionInfo.warnings`, shown by every UI surface).
- `transcriber.py` — wraps `faster-whisper`; transcribes each chunk and appends timestamped lines to a running transcript file. A stereo chunk is transcribed per channel (as float32 arrays, one Whisper pass each) and merged by segment start time into `[hh:mm:ss] Me: ...` / `[hh:mm:ss] Others: ...` lines (after `drop_echoes` removes Me segments that are near-duplicates of, or short verbatim fragments of, an Others segment within 4s — including the previous chunk's Others segments — the mic hearing the speakers); a mono chunk gives the plain `[hh:mm:ss] text` line. `model_path` (config `whisper_model_path`) loads a local CTranslate2 model directory with `local_files_only=True` for machines that can't reach Hugging Face.
- `summarizer.py` — defines the `Provider` interface (`summarize(transcript) -> Summary`) with `ClaudeProvider` and `AppleLocalProvider` (apfel, the default) implementations; this is the seam for adding other AI backends later. Each provider carries a `chunk_token_limit` (1800 for Apple's 4K-context on-device model, 12000 for Claude); `summarize_transcript` strips `[hh:mm:ss]` timestamps and the recorder's own `[warning]`/`[note]`/`[transcription failed …]` status lines (a small model otherwise quotes them into the minutes), map-reduces over chunks at that limit, and reports `on_progress(done, total)` so `stop` can show "Summarizing... chunk 3 of 7". The prompt asks for meeting minutes in the model's own words as bullets under Discussion/Decisions/Open questions, and `Owner: task` action items using the `Me:`/`Others:` labels. JSON parsing tolerates prose around the object, which small models add; `_text_as_minutes` renders a "text" that came back as a list or a headed mapping as bullet lines instead of leaking a Python repr, and `format_minutes` puts run-together headings ("Discussion: … Decisions: …") on their own paragraphs. `clean_summary_text` guards against the on-device model echoing the transcript back as the "summary": it strips `Me:`/`Others:` labels, drops lines copied verbatim from the transcript, and replaces the text with an explicit "Summary unavailable … Resummarize" notice when half or more of it was copied.
- `notes.py` — converts a finished session (transcript + summary) into a Markdown note, and backs `list`/`show` by parsing note frontmatter.
- `config.py` — loads/validates `~/.notetaker/config.yaml`. Defaults are fully on-device and install-free (`ai_provider: apple_local`, `system_audio: tap`, `capture_microphone: true`); optional `tap_process` (bundle id to tap exclusively) and `whisper_model_path` (offline model dir). `system_audio: blackhole` keeps the old loopback path. `update_config` resets `ai_model` to the new provider's default when the provider changes without an explicit model.
- `brew_formula.py` — generates one personal (non-distributed) Homebrew formula file into `Formula/` (gitignored — it bakes in this machine's absolute repo path) for the single `brew services`-managed background process, `notetaker-dashboard`, which runs the web dashboard and the menu bar together. The formula builds nothing itself; its `service do` block just points `brew services` at the `.venv/bin/notetaker dashboard` that `install.sh` already set up. Regenerated by `install.sh` on every run, which also retires the old separate `notetaker-menubar` service if it finds one (two services meant two menu bar icons) — see ADR 0003 for why `brew services` instead of hand-rolled LaunchAgents or a full formula/tap, and its amendment for why one service instead of two.

Key design decisions worth knowing before changing this system:
- Chunked polling was chosen over true overlap-merge streaming transcription for simplicity; see the spec's "Approach A vs B vs C" section before changing the recording/transcription model.
- A crashed recorder or a failed AI summarization call must never lose the meeting record — partial transcripts are always salvaged and saved, with the summary section noting the failure if summarization fails.
- The AI provider abstraction is intentionally minimal (one interface, one implementation) — it is a clean seam, not a plugin-loading system. Don't build out plugin discovery/config for it until a second provider is actually needed.
- macOS only for the MVP; the audio capture layer is the platform-specific piece if cross-platform support is added later.

## Development

- `./install.sh` — one-time setup (creates `.venv`, installs pinned deps).
- `.venv/bin/pytest -q` — full test suite.
- `.venv/bin/pytest -m "not integration" -q` — fast suite only, skips the two slower integration tests (a network-dependent faster-whisper download and a real-`brew` install/uninstall round-trip).
- Use `.venv/bin/python` / `.venv/bin/pytest` explicitly; there is no ambient install.
